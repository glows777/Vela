# Changelog

All notable changes to `@glows777/vela` are listed here. While Vela is on 0.x, a release that breaks the public API bumps the minor version and lists the break under **Breaking Changes** with how to migrate; patch releases don't break anything. See [API stability](docs/sdk.md#api-stability) for what counts as public.

## [Unreleased]

### Changed

- **Desktop conversations and settings are easier to use.** Vela replies render Markdown with copyable code; `⌘N` / `Ctrl+N` starts a new session, the composer grows as you type, and view-specific errors can be dismissed. Project, routine and model pickers support keyboard selection. Deleting a routine or removing a Lark chat requires confirmation, and Settings › Models can set the Thinking level for new sessions ([#531](https://github.com/glows777/Vela/issues/531)).

### Fixed

- Long sessions no longer get stuck at the pre-request context cap when the provider reports that the history fits. Opaque encrypted reasoning is not counted as text, and recoverable oversized requests get one compaction attempt ([#536](https://github.com/glows777/Vela/issues/536)).

## [0.8.0] - 2026-11-23

### Breaking Changes

- **`background_start` is gone; `bash` starts a background command.** `bash` takes `run_in_background: true`, runs the command through the session's execution environment and returns at once with the job id, so one shell tool covers foreground and background work. Replace `background_start({ command })` with `bash({ command, run_in_background: true })`, and remove `+background_start` from a `tools` list: an unknown name now fails at startup. `background_output`, `background_stop` and `background({ shellPath })` stay ([#429](https://github.com/glows777/Vela/issues/429)).

- **Esc no longer stops a background command.** A job belongs to its session, not to the run that started it: an interrupted run leaves it running and its exit still arrives; `background_stop`, `session.close()` and process shutdown stop it. A command still in the foreground when the run is interrupted is cancelled with it, as before ([#430](https://github.com/glows777/Vela/issues/430)).

- **Extension handler `ctx.cwd` now always means the session directory**, including handlers installed by user or SDK host extensions. Use factory-time `api.cwd` for the directory the extension instance was loaded from, and `ctx.cwd`/`ctx.session.cwd` for the active project. Project extensions and session-scoped CLI built-ins/MCP now use location-and-configuration snapshot instances; same-snapshot sessions share an instance, released after the last attached session closes. Storage-owning `memory` and `rag`, user custom extensions and explicit `-e`/SDK factories remain host-owned. Project provider/channel registration is diagnosed and refused; providers, credentials, listeners and durable `dataDir` remain host-owned. Handler ordering is host → project → core, so user-listed host handlers now precede project-discovered handlers. This is registration isolation, not a JavaScript sandbox ([#452](https://github.com/glows777/Vela/issues/452)).

- **Project-declared resources and runtime defaults follow the session location.** `skills`, `prompts`, default model/thinking, limits, automatic compaction and shell configuration are loaded from the session's trusted project instead of inheriting the startup project's merged settings. User configuration and explicit overrides remain shared; saved/manual model and thinking choices retain priority. Existing sessions keep their prepared snapshot, while new sessions see edited settings. Host `dataDir` remains a startup bootstrap value, and `serve` keeps its existing `defaultTools` exclusion. CLI `defaultTools` and TUI/RPC model cycling use the active session’s settings, and JSON mode reports the resumed session’s directory ([#452](https://github.com/glows777/Vela/issues/452)).

- **The `@glows777/vela-core` root entry no longer re-exports the extension contracts.** The 21 hook event types and five helpers stay public, but only from `@glows777/vela-core/extension-api`: `AfterProviderResponseEvent`, `BeforeAgentStartEvent`, `BeforeAgentStartEventResult`, `BeforeProviderRequestEvent`, `ContextEvent`, `ContextEventResult`, `InputEvent`, `InputEventResult`, `ProviderStreamEvent`, `SessionBeforeForkEvent`, `SessionBeforeForkEventResult`, `SessionBeforeTreeEvent`, `SessionBeforeTreeEventResult`, `SessionShutdownEvent`, `SessionStartEvent`, `SessionTreeEvent`, `ToolCallEvent`, `ToolCallEventResult`, `ToolResultEvent`, `ToolResultEventResult`, `TreePreparation`, `configString`, `configStrings`, `customMessageIfChanged`, `customMessageMissing`, `lastCustomMessage`. Every extension package already imports them from that subpath, and `@glows777/vela` still exports all 26 from its root, so umbrella users change nothing. `FetchFunction`, `TokenStatus` and `SessionEntryBase` also leave the core root and are internal to the package now: no import in the repo, docs or examples used them, and the public types whose shapes were flattened from them (`SessionUsage`, `SessionEntry`) still declare the same members ([#403](https://github.com/glows777/Vela/issues/403)).

- **`@glows777/vela` drops four exports nothing imported.** `FetchFunction`, `TokenStatus` and `SessionEntryBase` leave the umbrella with their core root copies, and `LoadedExtension` was an unused alias of the channel package's `LoadedChannelExtension`. Import `LoadedChannelExtension` from `@glows777/vela-channels` instead. `createVela().extensions()` returns `LoadedChannelExtension[]`. Each loaded extension includes `channels` ([#403](https://github.com/glows777/Vela/issues/403), [#458](https://github.com/glows777/Vela/issues/458)).

- **Newly saved sessions resume in their saved execution location.** Previously reopening a session without `cwd` used the host default, even when the session started elsewhere. New records restore their saved local cwd instead, including when a different cwd was passed on reopen. Existing records without a location keep the prior fallback; fork and clone inherit the active location. This is not a sandbox ([#410](https://github.com/glows777/Vela/issues/410)).

- Opening or resuming a session in another trusted project uses that project’s `.vela/SYSTEM.md` and `.vela/APPEND_SYSTEM.md`. Each file falls back independently to the user configuration. Explicit SDK and CLI prompt overrides retain priority, and ordinary wakes reuse the session snapshot ([#410](https://github.com/glows777/Vela/issues/410)).

- A first prompt (including a tool-free turn), fork or compaction that needs workspace instructions now fails if its session environment is unavailable. Retrying after recovery loads the instructions before contacting the model ([#410](https://github.com/glows777/Vela/issues/410)).

- Workspace instructions, skills and prompt templates follow each session's working directory. The CLI lists and completes the active session's resources. Local file, search, shell and background calls use the selected execution adapter. Background start returns a job ID, and stop aborts the job. Short shell output stays inline. Local sessions reuse Lark's private download on redelivery and topic forwarding ([#410](https://github.com/glows777/Vela/issues/410)).

### Added

- **Execution environments, Docker isolation, and credential proxy.** An SDK host can provide an `env` resolver for each session and inspect `ExecutionEnv` types; missing or unavailable locations fail loudly without falling back to the host. SDK hosts can read `session.location` and move an idle session with `await session.setLocation(location)`, preparing resources through the existing `env` resolver and persisting the target across reopen. Docker environments with `network: on` can use owner-configured GitHub credentials without putting the original token in the guest (this mode does not restrict network egress). On Linux Docker, owners can set `network: restricted` and an exact HTTPS host allowlist so unlisted destinations and direct connections are denied and a proxy outage never reopens networking. Lark files reach isolated sessions through a session-owned guest cache, forks and clones retain referenced uploads in their selected environment, a stopped workspace move leaves the current session in place, and operator installation diagnostics stay out of group replies ([#410](https://github.com/glows777/Vela/issues/410)).

- **Interrupted-turn recovery keeps finished steps.** `session.continueInterrupted()` reconciles and resumes the saved branch without a new user message; channel restart recovery no longer rewinds completed tool work. `ToolDefinition.replay` defaults to unsafe. Replaying requires both recorded and current safe policy, unchanged input/location, and fewer than five consecutive interruptions. Uncertain effects are reported, not silently repeated; this is not exactly-once external delivery ([#411](https://github.com/glows777/Vela/issues/411), [#454](https://github.com/glows777/Vela/pull/454)).

- **Graceful serve shutdown.** The first shutdown signal stops new admission and drains in-flight tools without starting another model/tool iteration. Results persist for restart recovery; a 30-second total cap logs and exits for uncooperative work. SDK hosts can opt into channel `dispose({ graceful: true })` and use `session.drain()` with their own deadline. Explicit Stop and default SDK disposal still cancel immediately ([#411](https://github.com/glows777/Vela/issues/411)).

- **Desktop app: Home, Local projects, and session side panel.** The window shows the projects list with each project's `Local` tag, creates a project from a folder (native picker or typed path), and keeps that folder's conversation: people's messages are bubbles, Vela answers in plain text, and a session started from the chat shows a card where its recorded title message sits. Asking a Local project for bigger work opens the session in a 480px side panel beside the chat with one state word (`Running`, `Queued`, `Waiting for an answer`, `Done`, `Stopped`), the active tool, Stop, and a reply composer. A session that asks a question joins Home's needs-you list and clears when answered. A failed run shows one error card and hides the reply that repeats it; the reply is the record that survives a restart. Below 1180px the panel floats over the chat, and each conversation keeps its place when switching projects or sessions ([#417](https://github.com/glows777/Vela/issues/417)).

- **Desktop app: Lark projects and Lark sessions.** Enabled groups appear under Projects with the `Lark` tag and open in the same project page and session panel as Local: the project chat is the group's history with people's names, a session is a topic with its state and the last line it recorded, and a message sent from the app posts in the group as the bot signed `Vela app`. Starting a session from Home opens a topic. A submission that did not plainly post says where it may have landed and re-reads history instead of resending; only a send that never reached Lark restores the draft. A group the app cannot connect to says Lark is off while Local projects keep working. New project → Lark lists enabled groups and can add a group after you mention the bot and confirm access for its members; the Lark setup helpers accept an optional set of group IDs to ignore during discovery ([#418](https://github.com/glows777/Vela/issues/418)).

- **Desktop app: first-run setup, Settings, and Routines.** With no usable model, the window opens on one setup screen: choose a provider, enter the key (checked with one small request before anything is saved), then a model. Settings › Models shows the same choice afterwards and names the file each row writes; Settings › General holds the Vela folder; Settings › Lark verifies app credentials, shows the connection and enabled chats, and can remove a chat or release the desktop connection for `vela serve`. `saveModelSetup`, `saveLarkSection` and `usableModel` are exported so a host writes `auth.json`, `models.json` and `settings.json` exactly as `vela setup` does. The Routines page groups scheduled routines by project with message, destination, creator, schedule and next run, supports in-place Edit and Cancel, and reports host validation errors ([#419](https://github.com/glows777/Vela/issues/419), [#420](https://github.com/glows777/Vela/issues/420)).

- **Desktop hosts can display and reply in Lark through the SDK.** The typed Lark host reads paged group and owned-topic history, posts as the bot with the person's signature, and can start or continue a topic. `LarkHost.chats()` answers from saved configuration, connected or not: every enabled group with its name when the built-in transport can read it, and its chat ID otherwise (a custom `LarkTransport` has no name lookup). A failed `submit` throws `LarkSubmitError` whose `outcome` is `not-sent`, `uncertain` or `posted` (with `messageId` when known), so a host re-reads history instead of resending. The host emits best-effort history updates and stores no second copy of Lark messages ([#416](https://github.com/glows777/Vela/issues/416), [#418](https://github.com/glows777/Vela/issues/418)).

- **Channel sessions can deliver a workspace file to their current conversation.** Lark posts native images or file attachments and reports Feishu’s error code and message if the post is rejected. Local hosts can retrieve a snapshot by message ID ([#402](https://github.com/glows777/Vela/issues/402)).

- **A running `bash` call can be moved to the background, and foreground timeouts hand off instead of killing.** `session.backgroundTasks(toolCallId?)` (and the RPC request `background_tasks` with an optional `tool_use_id`) takes over the named call, or every call the session runs in the foreground including your own `!` command; moving is recorded before it is promised. In the TUI, `Ctrl+B` moves the running command to the background (replacing the editor's cursor-left alias; use Left), the footer names running jobs, and `/tasks` (alias `/bashes`) lists or stops jobs (`/tasks stop <id>`). A foreground `bash` call that outlives `bashForegroundTimeoutSeconds` (default `120`, `0` for no budget; clamped by `bashForegroundTimeoutMaxSeconds`, default `600`) moves to the background instead of being killed; commands starting with `sleep` or sessions without `background_stop` keep the kill ([#430](https://github.com/glows777/Vela/issues/430), [#431](https://github.com/glows777/Vela/issues/431), [#432](https://github.com/glows777/Vela/issues/432)).

- **Print mode waits for background work and its result turns before exiting.** Text mode keeps the printed answer, and JSON mode includes the result events. Unattended background jobs have a 30-minute default deadline and a two-hour maximum ([#433](https://github.com/glows777/Vela/issues/433)).

- **GitHub Issue feeds support `issueLabels.all` and `issueLabels.any`.** Issue feeds can require every label in `issueLabels.all` and optionally match one in `issueLabels.any`; existing label arrays still match any listed label ([#423](https://github.com/glows777/Vela/issues/423)).

- **A GitHub review delivery names its inline comments.** A `pull_request_review` wake now carries the review id and the `GET /repos/<owner>/<repo>/pulls/<n>/reviews/<id>/comments` endpoint, so a subscribed topic can read the inline findings with its own tools; an event type outside the mapped webhook list is dropped with one bounded `debug` line instead of silently. A review payload without an id still wakes with the plain notice and no endpoint ([#487](https://github.com/glows777/Vela/issues/487)).

- **Active-project extension inspection.** `commands(sessionId?)` and `extensions(sessionId?)` inspect an existing prepared session. TUI command completion, `/extensions` and RPC command discovery use the active session, while no-argument calls keep the default-session view. Existing session snapshots and A's system/tool prefix stay unchanged when B opens; non-local project code and MCP remain unsupported rather than executing on the host ([#452](https://github.com/glows777/Vela/issues/452)).

- **Lark setup shows the discovered group name and chat ID before granting access**, with an ID-only fallback ([#517](https://github.com/glows777/Vela/issues/517)).

- **`@glows777/vela` exports `background`.** The umbrella re-exported every built-in factory except this one, so `import { background } from '@glows777/vela'` failed while `@glows777/vela-core` worked. It now re-exports `background` and `BackgroundOptions`, and the Background docs name the import path next to their `background()` example ([#408](https://github.com/glows777/Vela/issues/408)).

### Changed

- **A background command spills its output in the session's execution environment, and its two tools come with the extension.** The model keeps the last 2,000 lines or 50KB as the tail, and the start result also carries the output the command already wrote. Once the output passes those limits the environment spills the complete log to its own file, which the exit delivery names (`Full output: <path>`) and a stop returns, so `read_file` pages it — also in a session whose environment is not the host. `background_output` and `background_stop` are on whenever the `background` extension is loaded — the CLI loads it by default — instead of only where a channel turned them on, while a chat's narrowed `tools` list and a DM still drop them. A job also needs `background_stop`, so those sessions refuse `run_in_background` instead of starting a command nobody could stop. A started job's tool record carries `backgroundTaskId`, the start result carries the tail the command already wrote, and the background guidance now lives in the `run_in_background` parameter's own description instead of a prompt rule, so a session whose tools cannot use it is never told to ([#429](https://github.com/glows777/Vela/issues/429)).

- **A group session runs execution and background commands again.** The top-level session of a Lark group or a Local project chat keeps `bash`, `write_file` and `edit_file` and also gets `background_output` and `background_stop` (with `bash({ run_in_background: true })`), so a quick command such as `gh pr view` is answered where it was asked instead of being dispatched to a topic first. The conversation still stays available: a command that may keep running starts in the background, and its exit joins the group's own queue as a reply to the person's last message; a longer task still becomes a topic. A chat's narrowed `tools` list can drop any of these, and a DM is unchanged: it keeps its execution tools and still gets no background tools. This supersedes the 0.7 rule that hid the three execution tools from group sessions ([#421](https://github.com/glows777/Vela/issues/421)).

- The built-in Lark transport suppresses vendor SDK logs to keep credential payloads out of process output. This also suppresses SDK WebSocket warnings in `vela serve`.

### Fixed

- **Lark startup recovery no longer repeats feedback errors for expired or conflicting saved delivery intents**; terminal refusals settle locally without another chat message.

- **Hosted background jobs no longer disappear silently after a service restart.** The existing channel directory records jobs before execution, and startup queues one unknown-result input for each lost job without a new human message. A saved normal-result input or explicit Stop/close clears the record; SIGTERM shutdown preserves it. Durable input markers reconcile interrupted notification persistence without claiming exactly-once remote replies ([#411](https://github.com/glows777/Vela/issues/411)).

- **Lark final replies and topic-title sends carry a durable delivery identity.** A saved send intent reuses its UUID only within Lark's one-hour deduplication window; an acknowledged send is not repeated after restart. Expired uncertain sends fail as unknown instead of sending with a new identity. Topic tools remain unsafe to replay, and forwarding, progress cards and status notices are not covered by this bounded guarantee ([#411](https://github.com/glows777/Vela/issues/411)).

- **Normal follow-up after a mid-tool restart repairs missing results before the new message.** SDK `resume()` then `prompt()`, and CLI interactive/print/JSON/RPC follow-ups, now use the existing result reconciliation instead of failing with `AI_MissingToolResultsError`. Finished results remain intact and unsafe effects are not replayed. Histories already damaged by an older failed follow-up stop with an explicit diagnostic before another repair or execution, rather than silently dropping that message ([#455](https://github.com/glows777/Vela/issues/455)).

- **The prompt's intro paragraph no longer claims tools a session may not have.** It said the agent works by "reading, searching and editing files, running commands" even when the session was narrowed to `read_file` (the SDK's `tools`, or a chat's tool list), while `<tools>` and `<rules>` were already accurate. The intro now says only that the agent works through the tools of this session, so a session without `bash`, `write_file` or `edit_file` is not told it can edit files or run commands, and a normal CLI/SDK session still describes those tools in `<tools>` ([#406](https://github.com/glows777/Vela/issues/406)).

- **A chat session that something else opened first now gets the chat's tool split.** When a host opened the chat's session before the gateway did — the SDK's `vela.session(id)` before the first message, or a read after idle cleanup closed it — core kept the tools that session was constructed with, because it reads `tools` only when it constructs a session. The group session then missed the background tools a hub gains and kept `channel_wait_for_input`, which only a topic can use. The gateway now applies the split when it opens an existing session too: a tool its chat turns off is removed, a hub's background commands are added, and a tool allowlist that session already had stays as narrow as it was, so a chat's `tools` list cannot add a tool back and a `session_start` handler still has the last word. Every channel shares it ([#405](https://github.com/glows777/Vela/issues/405)).

- **A message the Local project chat refuses says why it was refused.** Local's message schema gives the two `text` rules a sender can fix their own words — `Message is too long (max 100000 characters)` past Local's limit and `Message must not be empty` — while any other shape failure keeps `Invalid JSON request body`. The desktop shows that reason as it is, without Electron's `Error invoking remote method '…': LocalError:` wrapper ([#469](https://github.com/glows777/Vela/issues/469)).

- **The desktop project header keeps its name on one line, and the first-run custom provider form stays within the default window.** A long folder path ellipsizes beside the name with the full path on hover, the custom provider form keeps **Verify and save** in view and shows provider rejection reasons alongside retry, and project headers keep their source tag and folder path visible even with a long title ([#470](https://github.com/glows777/Vela/issues/470), [#513](https://github.com/glows777/Vela/pull/513)).

## [0.7.1] - 2026-11-18

### Fixed

- **A channel's system prompt no longer changes with the kind of wake.** The group and topic sections appended a clause per input — untagged discussion, a hand-off note, or nothing — so a session that switched between a person's message, untagged discussion and a hand-off note rewrote its system prompt, and every prefix-caching provider reread the whole conversation at full price. Each session kind now has one fixed section, chosen from the saved chat record, and an untagged input carries a short marker in the text the model receives instead ([#445](https://github.com/glows777/Vela/issues/445)).

### Changed

- **The date and the timezone left the system prompt.** After the git branch left `<env>`, that section still rendered the local calendar date and the IANA timezone on every request. A session that continued past midnight received a new system prompt on the next request. The cached prefix was rewritten. `<env>` now names only the operating system and the shell. The date, the time of day and the timezone are not injected into the system prompt or into a message. The model reads the clock with `date` when it needs it. Pi's system prompt has no `<env>` section. Vela keeps `<env>` for those two session-stable facts. A faux scenario checks that one session's assembled system prompt is the same bytes across a local date rollover. The scenario does not prove a cache hit from a real provider ([#444](https://github.com/glows777/Vela/pull/444)).

- **The git branch left the system prompt.** `<env>` carried `git branch: <name>` read from the working tree on every request, so anything that checked out a branch in that tree during a session — another session sharing the checkout, or a git command the agent itself ran — rewrote the request's cached prefix. Every provider that caches by prefix then re-read the whole conversation at full price: on one Lark group that was 20 of 694 requests in a day and 55% of its cost, with 242k–355k tokens re-sent each time. The branch is no longer injected at all, like pi. `<env>` was left with the date, time zone, OS and shell, and the model reads the branch with `git branch --show-current` when it needs it, so a stale branch cannot mislead it either. Sharing one working tree between parallel tasks is still the underlying hazard; separate worktrees for parallel work are the intended fix and are not part of this change ([#442](https://github.com/glows777/Vela/issues/442)).

## [0.7.0] - 2026-11-16

### Breaking Changes

- **The unused `memoryConfig` export is removed.** It was exported from `@glows777/vela-core` and `@glows777/vela` but had no consumer: memory reads `extensionConfig.memory` directly, so configuration and behavior are unchanged. Import nothing in its place ([#345](https://github.com/glows777/Vela/issues/345)).

- **Session permissions and the built-in permission gate are removed.** Remove `SessionOptions.permissions` and imports of `PermissionRules`, `PermissionDecision`, `decidePermission`, `permissionGate` and `permissionGateConfig`. `session.toolDecision(name)` is also removed; use `session.getActiveTools()` to inspect currently exposed tools. Use `tools` (an allowlist or `+name` / `-name` modifiers) to control per-session tool availability. Replace confirmation rules with a user `tool_call` extension that checks `ctx.hasUI`, asks through `ctx.ui.confirm` and blocks when no UI is attached or the user declines; see [confirm-dangerous.ts](examples/extensions/confirm-dangerous.ts). Remove `builtin:permission-gate` entries from settings and CLI arguments: they now fail as an unknown built-in. Vela ships six selectable built-ins. Tool selection and confirmation are not isolation: every enabled chat, Local token and webhook input reaches the same OS account and can access its other sessions, memory and credentials ([#348](https://github.com/glows777/Vela/issues/348)).
- **Top-level group channel sessions no longer run local tools.** The top-level session of a group channel (a Lark group or a Local project chat) hides `bash`, `write_file` and `edit_file`, and a chat's configured `tools` list cannot add them back; topics keep the tools their chat selects. Requests that need execution, file changes or a longer exchange go through a topic. DMs and topic sessions are unchanged ([#336](https://github.com/glows777/Vela/issues/336)).
- **Issue feeds are a strict label allowlist.** `extensionConfig.channel.eventReceiver.github.issueLabels` must name at least one label for `github:<owner>/<repo>#issues` to deliver anything: an empty list, including an omitted option, now accepts no Issue event, where 0.6.0 delivered every Issue except `labeled`. Add the labels that should wake the feed, for example `"issueLabels": ["to:vela"]`. Existing subscriptions are not rewritten, and PR subscriptions stay independent of the list ([#356](https://github.com/glows777/Vela/issues/356)).

### Added

- **A session hands results produced outside a turn to its host, and reports that work.** `SessionOptions.host` is `{ deliver(text: string): void | Promise<void> }`: a host that owns a queue for its session's out-of-turn results (a channel supplies its topic's input queue) gets them there, so a background command's exit arrives as an ordinary queued input with the topic's anchor, progress card, reaction and Stop, while a host without one still gets the custom message that starts a turn. `session.hasWork` is true while such work is still running, so channel idle cleanup keeps that session open. The two replace the untracked global-symbol contract between `@glows777/vela-core` and `@glows777/vela-channels` with a typed one ([#388](https://github.com/glows777/Vela/issues/388)).

- **The system prompt is built from named sections, and can be replaced.** The prompt is rendered from ordered, tagged sections — the intro paragraph, `<tools>`, `<deferred_tools>`, `<rules>`, `<docs>`, `<addendum>`, `<project_context>`, `<skills>`, `<cwd>`, `<env>` and one section per extension (`<memory>`, `<channelTopic>`, …) — like pi's `buildSystemPromptSections`. A tool now contributes to the prompt while it is active: `ToolDefinition.promptSnippet` supplies its line in `<tools>` and `promptGuidelines` supplies rules in `<rules>`, so a session that hides `bash`, `write_file` or `edit_file` (a top-level group chat, for example) is no longer told to use them, and the `tool_search` advice appears only when something is deferred. `<docs>` names the installed README, `docs/` and `examples/`; `createVela()` from `@glows777/vela` points at its own package, and core SDK users set `docs` themselves. A prompt replaces the default one through `--system-prompt <text|file>`, `~/.vela/SYSTEM.md` or `<project>/.vela/SYSTEM.md` (trusted projects; the project file wins), or the SDK's `systemPrompt`: it becomes the intro and `<tools>`, `<rules>` and `<docs>` are dropped. `before_agent_start` handlers get `event.systemPrompt`, the prompt as earlier handlers left it, and can return `{ systemPrompt }` to replace the whole prompt for that turn. `inspectSession()` returns the rendered `systemPrompt` next to `systemPromptChars` ([#379](https://github.com/glows777/Vela/issues/379)).

- **Background commands.** The new built-in `background` extension adds `background_start`, `background_output` and `background_stop`: a command runs detached, its output is kept as a bounded in-memory tail (the last 2,000 lines or 50 KB), and when it exits on its own the session gets one message with the exit state and tail (a stop returns the tail in the tool result instead). In a channel topic that result enters the gateway queue like any other input and is answered as a new reply in the topic, and the topic session stays open while a command runs so idle cleanup cannot kill it; in the CLI and SDK it is a hidden custom message that starts a turn or joins the current run. `background_stop`, Stop, session close and process shutdown end the commands without starting another run, and nothing is persisted, so an old id after a restart explains that it may have ended with the restart. `background()` is a new export of `@glows777/vela-core` ([#336](https://github.com/glows777/Vela/issues/336)).

- **Background commands are topic tools.** The three tools are off by default (`activeByDefault: false`): a channel topic session turns them on, while the top-level group session and other non-topic sessions keep them off even when a chat's `tools` list names them. A CLI or SDK session opts in with `+background_start`, `+background_output` and `+background_stop` ([#336](https://github.com/glows777/Vela/issues/336)).

- **Local SDK core without HTTP.** `local({})` opens no listener; supplying a token keeps the authenticated HTTP/SSE adapter. `vela.channel('local')` exposes typed project, visible-history, composer-submit and event methods over the same store and runtime. SDK events share IDs with SSE while reset and disconnect stay transport-local. Existing Local data, CLI configuration and HTTP v1 behavior remain compatible ([#312](https://github.com/glows777/Vela/issues/312)).

- **SDK host access to channels.** `vela.channel(name)` exposes enabled session snapshots, session/status subscriptions, durable submission, run-bound Stop, idle routine management and `{ connected, error? }` connection observation. Lark reports real SDK readiness and reconnect changes; owned topic follow-ups require matching logical IDs and a real reply anchor. Local supports the same host controls ([#312](https://github.com/glows777/Vela/issues/312)).

- **Session management for SDK hosts.** `vela.listSessions()` summaries now include the session's working directory and, when a host opened it for a channel, the channel name. `vela.setSessionArchived(id, archived)` archives or unarchives a saved session without opening it, and archived sessions are left out of `listSessions()` (and the interactive picker) unless `{ includeArchived: true }` is passed. `vela.searchSessions(text)` searches saved sessions' user and assistant messages and returns the session id with a short match. The flag is a new append-only `session_archived` entry. The session header gains an optional `channel` field, and a first channel binding that arrives after the session was written appends a `session_channel` entry ([#314](https://github.com/glows777/Vela/issues/314)).

- **Routines can be edited in place.** `ChannelRuntime.routines.edit(sessionId, id, { message?, schedule? })` and the chat-scoped `ChannelHost.routines.edit(target, id, { message?, schedule? })` change an existing routine's message and/or schedule while keeping its id, creator, creation time and logical target. Validation matches creation; an id outside the calling chat returns `undefined`, and the `channel_routines` tool reports `edited: false` instead of pretending to change it. A schedule change records an optional `scheduleUpdatedAt` watermark, so a time that already passed today is not delivered late, and the new schedule survives a restart. The `channel_routines` tool gains the `edit` action ([#314](https://github.com/glows777/Vela/issues/314)).

### Changed

- **The prompt only describes tools the session has, and extension sections are tagged.** `<tools>` lists the active tools that have a `promptSnippet`, and the `tool_search` and "read before you edit" rules come from the tools themselves instead of always being present. Every extension section is wrapped in `<name>`, so prompts differ textually from 0.6.0; a section name that is not a valid tag is made safe, and a name that matches a built-in section adds a second section with that tag instead of replacing the built-in one ([#379](https://github.com/glows777/Vela/issues/379)).

- **Queued passive discussion is evaluated together.** Top-level group messages that arrive while an evaluation is running no longer run one by one: every passive input already waiting when the next evaluation starts is read in that one evaluation, in arrival order with its own sender and send time, and a reply goes to the newest input. Explicit @ messages, topics and DMs still run separately, and each merged input keeps its own `channel.input` marker for restart deduplication ([#336](https://github.com/glows777/Vela/issues/336)).

- **Issue feeds honor their label allowlist.** An Issue without one of the `issueLabels` sends no `opened`, `closed` or comment event, and `labeled` stays limited to the listed labels ([#341](https://github.com/glows777/Vela/issues/341)).

### Fixed

- **A background command is stopped through the same process-tree code as `bash`, including on Windows.** `background_stop` used to signal only the shell on Windows, leaving the command's descendants running; it now uses the bash tool's `taskkill /T /F`, from one shared implementation that also keeps the POSIX process group and its SIGTERM-to-SIGKILL grace. The output limits and the tail cut (last 2,000 lines or 50 KB, cut at line starts, a single huge line kept as its cut end) are likewise one implementation for both tools ([#388](https://github.com/glows777/Vela/issues/388)).

- **A background command's id is forgotten once its result is delivered or stopped.** The job and its in-memory tail no longer stay for the life of the session. Asking `background_output` or `background_stop` for that id afterwards explains that it has finished and its result was delivered (or returned by the stop), or that it ended with a restart or session close ([#388](https://github.com/glows777/Vela/issues/388)).

- **The no-model message names the built-in DeepSeek key.** `No model available…` offered `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` and `OPENROUTER_API_KEY` although `DEEPSEEK_API_KEY` also picks a default model, so the guidance hid a provider that works ([#390](https://github.com/glows777/Vela/issues/390)).

- **A Lark image is no longer downloaded without a size limit.** Image downloads stop at the same **20MB** limit as file attachments, from one shared constant: an explicit request receives the too-large reply, a passive image leaves an operator diagnostic, and the image does not reach the model. An oversized image in history keeps its `[image]` line instead of failing the context read ([#389](https://github.com/glows777/Vela/issues/389)).

- **A passive flood no longer wedges the group session.** Queued untagged top-level discussion is merged only up to 400 KB of prepared text: the newest inputs that fit are evaluated, the older ones leave the queue, and the group gets one short notice per session that discussion was skipped. Before, a 1,000-message flood (or one 5 MB message) became a prompt above `maxInputTokens`; the rejected turn stayed in the history and every later personal @ failed with `Context exceeds the safe input size`. A top-level group prompt the context guard rejects before the model call now drops that turn's input and records the branch, so even a session whose stored history is already too large recovers on the next message instead of failing every later one ([#386](https://github.com/glows777/Vela/issues/386)).

- **Dream lets the model fix its own unusable reply once.** A reply that cannot be parsed or applied — a JSON error, a missing or invalid field, an operation naming a file the model was not shown — is now answered once with the same input, that reply and a one-line error, and the corrected reply is validated exactly as before. A second unusable reply still fails the run and retains the inbox for the usual 20-turn or 24-hour gate, so a blind retry no longer repeats the same omission. `reason` and a note's `description` are optional (the report says `no reason given`, the index description falls back to the name), and validation errors are one line instead of a multi-line Zod dump. Both calls are recorded as dream usage ([#382](https://github.com/glows777/Vela/issues/382)).

- **Dream keeps a consolidation the model wrapped loosely.** A reply that puts the JSON object first and then a stray closing fence or trailing prose is accepted, where Node's parse error used to discard the whole batch and retain the inbox for a retry; text before the object, a second object, an array or a second fence block still fails, and every operation keeps the same schema, filename and source checks. A failed run's `.dream/log.md` entry also keeps the last 500 characters of the reply, so the next unexpected shape is diagnosable from the store alone ([#380](https://github.com/glows777/Vela/issues/380)).

- **A failed progress update no longer freezes the card or reads as a stopped turn.** A Lark card write that fails transiently is retried after 1, 2, 4 and 8 seconds and the card resumes updating, so one network reset no longer leaves it at its first state for the rest of the run; five consecutive live failures end the attempts. The final card, written after the answer and the outcome reaction, is retried after 1 and 2 seconds so a dead card cannot hold `DONE` back. One input reports its presentation failure once: a live failure says the task keeps running, and a final one says the task has ended only when nothing was reported earlier. `channel_error` carries `source: 'feedback'` only for these presentation failures — admission, preparation and command failures stay task failures — and `vela serve` logs `Feedback failed: …` instead of `Turn stopped: …` for them ([#367](https://github.com/glows777/Vela/issues/367)).

- **TUI hints name the key the platform actually has.** The queue hint, the header line and `/hotkeys` now derive their labels from the bound keys, so macOS reads `Option+Enter` and `Option+Up` (the Alt key does not exist there) while Windows and Linux keep `Alt`. The paste-image shortcut keeps its `Ctrl+V` / Windows `Alt+V` split from the same table, so the text cannot drift from the binding ([#369](https://github.com/glows777/Vela/issues/369)).

- **Local startup cannot outlive disposal.** Stopping while Local storage is loading prevents the later HTTP listener and observers from being created, so `dispose()` cannot leave a hidden loopback server running ([#312](https://github.com/glows777/Vela/issues/312)).

- **A saved channel stays bound after resume.** `resume()` restores the channel from the session header or the last `session_channel` entry. Binding a different channel afterwards throws `SessionRoutingConflictError`, and supplying the saved channel again does not append another entry ([#354](https://github.com/glows777/Vela/issues/354)).

- **Help and the empty `--list-models` message name the built-in DeepSeek key.** `vela --help`, the empty `--list-models` message and `docs/cli.md` now list `DEEPSEEK_API_KEY`; help and docs also add `OPENROUTER_API_KEY`, and the `--model` help line names all four built-in providers ([#330](https://github.com/glows777/Vela/issues/330)).

- **AI SDK warnings stay in the chat log.** Interactive mode redirects `AI_SDK_LOG_WARNINGS` into notices, so a compatibility warning (for example the `propertyNames` one from MCP record tools on OpenAI-compatible models) no longer writes over the TUI and appears once per session instead of on every request. Print, JSON and RPC modes still log it on stderr ([#337](https://github.com/glows777/Vela/issues/337)).

- **Actionable agent failures.** Failed `agent_end` events include `errorKind` for auth, billing, rate limits, network failures, context overflow, provider failures and unknown errors. Notes retain source session IDs, concurrent edits skip the whole operation batch without consuming its inbox, `/memory` shows audit status, and dream usage is accounted for. Dream requires memory permission `allow`; approval-required sessions neither contribute inbox data nor run consolidation. Failed or skipped runs wait for 20 new turns or 24 hours before automatic retry; `/memory` shows their outcome and manual retry stays immediate. Disable automatic runs with `extensionConfig.memory.dream: false`. Memory indexes no longer discard old entries; truncated injection points to search ([#306](https://github.com/glows777/Vela/issues/306)).

- **Independent microcompaction switch.** `limits.microcompact` (default `true`) turns off folding old tool results only; threshold summaries and overflow compaction keep following `autoCompaction`, and `microcompactThreshold` / `minMicroSavings` still tune when it runs ([#290](https://github.com/glows777/Vela/issues/290)).

- **Per-group model and thinking level.** Lark `chats` entries accept `model`, `thinkingLevel`, `topicModel` and `topicThinkingLevel`. Topics inherit the group's values, then the user's `defaultModel` / `defaultThinkingLevel`; unknown thinking levels fail loading and an unresolved model fails when its session opens. `ChannelDefinition.sessionOptions` gains optional `model` and `thinkingLevel`, so other channels can supply them too. A configured value is applied again whenever the session opens, so a changed chat entry takes effect on resume; a mid-session `/model` or `/thinking` choice survives a resume only for a value the chat entry does not configure ([#285](https://github.com/glows777/Vela/issues/285)).

The authenticated `127.0.0.1:8788` listener supplies project hubs, task sessions, visible message history, automatic task steering and run-bound Stop. Identity/history persist within the same deployment/data directory; SSE reconnects always reset and reload snapshots, with no replay or client-ID deduplication. Local stays separate from webhook port 8787 and must not be tunneled. No app UI, remote-access service or existing-data migration is included. See [Local protocol and examples](docs/channels.md#local) ([#281](https://github.com/glows777/Vela/issues/281)).

- **Gateway-owned channel observation.** `ChannelRuntime.onSession()` publishes detached snapshots and exact run transitions from preparation through completion and queue release. Local SSE uses these transitions rather than polling or model-event guesses, including Stop before model work and preparation failures. Provider/framework error messages remain useful on Local as on Lark; transport-level storage/admission failures retain generic HTTP 503 responses.

- **Repository Issue feeds for GitHub events.** A group subscribes once to `github:<owner>/<repo>#issues` and receives ordinary Issues opened or closed, Issues labeled with a configured `issueLabels` entry, and ordinary Issue comments; a topic keeps subscribing to its own `github:<owner>/<repo>#pr/<n>`. Both routes share the existing repository webhook, and each `issue_comment` matches exactly one key, so PR feedback is not duplicated into the group. Issue events are never final, so closing an Issue keeps the feed, while closing a PR still removes only its own subscription. `issueLabels` defaults to empty, which ignores every `labeled` action. Setup registers the `issues` event, and rerunning it updates the existing hook's event list ([#332](https://github.com/glows777/Vela/issues/332)).

- **GitHub webhook setup.** `vela setup github owner/repo --url https://public-origin` saves private user receiver settings and creates or updates matching repository hooks through GitHub CLI 2.57 or newer. Authentication checks use only the active account; an expired inactive account does not trigger manual fallback or print the secret. Missing authentication leaves manual setup instructions. Topics with GitHub ingress are guided to subscribe to PR events rather than poll; tunnels and live delivery remain operator checks ([#274](https://github.com/glows777/Vela/issues/274)).

- **Adapter-facing channel runtime.** Channel adapters can declare topic capabilities and use shared dispatch/routine tools, explicit conversation kind, admission receipts, scoped session snapshots, run-bound Stop and persisted status-line notifications. Lark and Local exercise the same public channel contract ([#281](https://github.com/glows777/Vela/issues/281)).

- **Custom provider setup.** The setup wizard supports OpenAI Chat Completions, OpenAI Responses and Anthropic Messages endpoints, optional headers and model capabilities, and verifies the chosen configuration before saving. Optional headers and context window use direct inputs: empty Enter keeps existing values or defaults, while Escape cancels without saving. Existing provider and model fields are preserved when unchanged ([#289](https://github.com/glows777/Vela/issues/289)).

- **Built-in DeepSeek.** Use `DEEPSEEK_API_KEY`, `auth.json` or `/login deepseek`; first-run setup selects `deepseek/deepseek-flash` on Responses. `deepseek-v4-pro` declares provider-hosted web search at model level; flash does not. Explicit compatibility flags also support DeepSeek gateways with other hostnames ([#289](https://github.com/glows777/Vela/issues/289)).

- **Provider-hosted web search.** Supported OpenAI Responses and Anthropic Messages models can search without a separate search key. Existing independent search and per-call approval remain available; provider search charges are not included in token cost estimates ([#293](https://github.com/glows777/Vela/issues/293)).

- **A built-in `todo` extension.** The model keeps one task list up to date for multi-step work. The whole list travels in every `todo` call, so the latest call in the session is the current list and a resumed session reads it back from history; no new event type or storage is involved. Lark's progress card shows the list above the tool rows — starting each new run in a topic, including one after a restart or `!restart`, from the list stored in the session — capped at ten items. It is on by default in the CLI; the SDK loads it explicitly ([#282](https://github.com/glows777/Vela/issues/282)).

A connection message verifies sending; card callbacks remain a manual check. ([#272](https://github.com/glows777/Vela/issues/272)).

Configure built-in providers, DeepSeek or an OpenAI-compatible endpoint, verify a model and save user-level settings. Verification sends a small request that may incur a charge ([#270](https://github.com/glows777/Vela/issues/270)).

## [0.4.0] - 2026-10-27

### Added

- **`vela serve` runs the configured channels without the TUI.** The first argument `serve` selects a new run mode: no terminal UI and nothing on stdout, one line per channel event on stderr with a local timestamp (`channel_message`, `channel_reply`, `channel_error`, terminal escape sequences stripped and text cut to 80 characters), and SIGINT/SIGTERM stop the channels through the existing `dispose()` and exit 0. Enable it with `+builtin:permission-gate` in settings or `-e builtin:permission-gate`; the SDK adds `permissionGate()`. `loadConfig` gains `defaultOffBuiltins` for callers that pass `builtins` themselves. See [Built-in extensions](https://github.com/glows777/Vela/blob/v0.4.0/docs/built-in-extensions.md#permission-gate).

Silence, an empty answer or a topic handoff removes the marker with nothing left behind; passive input still gets no progress/control card. Custom channels receive the new `silent` value on `finish(outcome)`.

### Changed

- **The TUI no longer starts channels.** Channels run only under `vela serve`, so an interactive `vela` session no longer opens a second connection to the chat service or a second writer to the single-process channel directory, and channel messages no longer appear in the chat log. The SDK is unchanged: `vela.startChannels()` still starts them in your own process. See [Channels](docs/channels.md) and [CLI](docs/cli.md#interactive-mode).

- **The core prompt has output rules, an `<env>` block, and Feishu group history carries send times.** The new rules ask for the answer first, a length that matches the question, no restating and no unrequested next steps, and say something was saved, sent or done only after the tool call for it succeeded. `<env>` adds the date (not the time of day, so the cached prompt prefix only changes once a day), time zone, OS, shell and git branch; the branch comes from the session working directory's `.git/HEAD`, with no subprocess. Each `[Chat since last reply]` and `[Question]` line now starts with the message's local `HH:MM`.

- **The core prompt's length rule is concrete, and the separate concision rule is gone.** "Match the response length to the question" now asks for a short paragraph plus at most three bullets, the main path and the facts asked for, not every branch, option, test or per-step file:line, and no closing restatement. This replaces "Be concise and direct in your responses.", which said the same thing less clearly, so the core rules are nine instead of ten. This is a prompt change: there is no length check in code.

- **Only four core tools are on by default (like pi).** A new session declares `read_file`, `write_file`, `edit_file` and `bash` (plus `tool_search`); `grep`, `find` and `list_directory` stay registered but off, so models that search with `bash` no longer pay for their schemas. Enable one with `--tools +grep` (or `--tools +grep,+find,+list_directory`) or a list of only `+name` / `-name` entries in the new `defaultTools` setting; plain names still select exactly those tools, and a project's `defaultTools` entries adjust the user list. The SDK `tools` option takes the same entries. Tools that extensions register are unaffected. See [Tools](docs/tools.md), [Settings](docs/settings.md#defaulttools) and [CLI](docs/cli.md).

- **Feishu tools and startup stay inside Feishu.** The seven `feishu_*` tools are no longer declared to plain CLI or SDK sessions: `ToolDefinition.channel` names the channel that owns a tool, and a session opened for another channel (or no channel) hides and denies it. Group and topic sessions keep their existing tool sets. A Feishu channel without `appId`/`appSecret` now returns `false` from `start()`, so the gateway skips its startup line, routines and recovery instead of printing `✓ feishu started`.
- Extension tool registration rejects non-Zod input schemas immediately with the extension and tool names. The CLI reports the failed extension and continues loading other extensions; internal MCP JSON schemas remain supported.

- **A Feishu topic opens with a short title, and the brief stays private.** `feishu_start_topic` takes `title` and `brief` instead of one `task`: the title is posted as the topic's first visible message and becomes its label in `feishu_list_topics`, while the brief goes only to the topic session with the sender's name. The channel prompt asks for a one-line title and keeps the plan out of both texts. Custom `FeishuTransport` implementations receive the title in `startTopic`; `ChannelRuntime.dispatch` takes an optional label for the directory entry.

- Compaction now produces a structured free-text checkpoint with progress, next steps and code-derived read/modified file lists. Summaries use the model output limit instead of a fixed 8,192-token cap; incomplete or failed summaries leave history unchanged.

- **Tool results sent to the model are plain text.** Bash no longer adds a timestamp or a `StoredToolResult` JSON wrapper; only truncated output includes a full-output path. Default and web result limits are now 50K characters, with head previews for generic/web results and the existing bash tail. The system history guide is removed; compaction keeps the earlier-output location. Result files and crash-recovery history are retained, and old `StoredToolResult` sessions still load. SDK consumers reading tool messages should handle text results instead of expecting `StoredToolResult`.

- **Memory and knowledge-base context arrives as messages after the cached prefix.** The memory index and the RAG source list are appended when they change instead of being rebuilt into the system prompt; the fixed memory usage rules stay there. Saving a memory, deleting entries or ingesting a document no longer rewrites the cached prompt prefix. Loading a deferred tool with `tool_search` still costs one cache miss.

### Fixed

- **Feishu topic titles have a budget, and a work request no longer stays in the group.** The group prompt and the `feishu_start_topic` description ask for a one-line title of at most 40 characters that names the task, with requirements, method and status left out, and say that any request needing work must become a topic while only short questions are answered in place. The brief keeps the requirements. This is a prompt change: there is no length check or truncation in code.
- **A provider content filter fails the run instead of ending it silently.** When a model response stops with AI SDK finish reason `content-filter`, the assistant message ends with `stopReason: 'error'` and `errorMessage: "Provider stopped the response: content_filter"`, the run ends with `agent_end` `reason: 'error'`, and `prompt()` rejects with that reason, so the TUI, `-p` / `--mode json` and channels show it. Text streamed before the filter stays in the context; the response is not retried.
- **A Feishu group no longer repeats a mention already handed to a topic.** After Vela opens a topic for a top-level message, or forwards that message into a topic, later `[Chat since last reply]` scans stop at that trigger's create time. Messages other people send after the trigger still appear. Vela remembers the stop for this process. After a restart the scan falls back to an own-app message in the group list.
- **Switching models no longer replays the previous model's reasoning.** An assistant message records the model that produced it (`producedBy`, `provider/modelId` as the AI SDK names the model, so the same model chosen by name or as an object has one identity), and a request leaves out reasoning another model wrote — its signature or encrypted content is only valid for the model that wrote it, and the new model could carry it into the visible answer. Text and tool calls stay, the history keeps everything, and switching back sends the earlier model its own reasoning again, also after a resume.
- **A resumed session declares the deferred tools it loaded.** `resume()` reads the session's `tool_search` results and declares the tools they loaded again, so the model goes on using them without searching a second time. Sessions without such results are unchanged.
- Routine lists show a readable topic task without its opaque root message id; routine ids remain available for cancellation.

### Breaking Changes

- **The built-in bash gate is gone, and so is `security_warning`.** Vela no longer rejects bash commands that match its old pattern list: a command runs unless a session `permissions` rule, a hook or a `tool_call` extension blocks it. `src/security/bash-classifier.ts` and the `security_warning` event are removed; listeners should drop that branch. For a confirmation prompt on a smaller pattern list, enable the new opt-in `permission-gate` extension. Commands the old gate rejected for no good reason (a harmless recursive force-delete under a temporary directory, a `grep` whose pattern contains such a command) now run. See [Security](docs/security.md).

- **Session roles are gone (like pi).** `Role`, `ChannelDefinition.roleFor`, `session.role` / `vela.session(id, { role })`, the `/role` command and the `Role` line of `/status` are removed. Every session has the same tools, prompt and commands, and an enabled chat is trusted as a whole. Restrict a session with `permissions` (`{ bash: 'ask', write_file: 'deny' }`) and `tools` instead; a tool without a rule is allowed. Guest and collaborator sessions, and their prompt differences, no longer exist. See [Security](https://github.com/glows777/Vela/blob/v0.4.0/docs/security.md#per-session-permissions).

- **`tool_search` searches by keyword and loads tools instead of returning schemas** (like pi). It takes `query` (keywords, or exact tool names separated by commas) and an optional `limit` (default 8), ranks deferred tools with BM25 and loads the best matches for the model's next call; the result lists the loaded tools and each namespace's `instructions` once. The system prompt names each namespace (such as an MCP server) once with its tool count instead of listing its tools. Faux scenarios that read the old JSON result of `tool_search` need updating. See [Tools](docs/tools.md#deferred-tools-and-tool_search).
- An extension tool whose name already starts with `<extension name>_` is no longer prefixed again (`web_x` from the `web` extension stays `web_x`, not `web_web_x`).
- **Prompting a saved session that was not resumed fails** with `Session <id> already has saved history: call resume() to continue it, or use another session id`. Before, the old history was silently overwritten at the end of the prompt. Call `await session.resume()` first, or use a new id.
- **The built-in `openai` provider uses the Responses API** (`openai-responses`, like pi) instead of Chat Completions. For an OpenAI-compatible service behind `OPENAI_API_BASE_URL` that only speaks Chat Completions, set `"api": "openai-completions"` on `openai` in `~/.vela/models.json`, or add the service as its own provider.
- **An unsupported thinking level is clamped instead of failing** (like pi): a model with `reasoning: false` runs with `off`, and `xhigh` / `max` fall back to `high` unless the model's catalog entry supports them. `max` is now sent to the AI SDK as `max` (it was `xhigh`), and `off` sends `reasoning: 'none'` to models without `reasoning: false`. `/thinking`, Shift+Tab and RPC `get_available_thinking_levels` offer only the levels the model supports. See [Thinking levels](docs/models.md#thinking-levels).
- **`vela.models()`, `/model`, `--list-models` and RPC `get_available_models` list only available models**: those of providers that have a credential, like pi. `vela.models({ all: true })` returns every listed model.
- **`ProviderDefinition.createModel(id, ctx)`** gets a second argument with `ctx.credential()`; providers that ignore it keep working. `ModelRegistry` takes a `CredentialStore` as its second argument.
- **Without `--model`, `defaultModel` or `OPENAI_API_MODEL_NAME`, Vela picks pi's default model** of the first built-in provider that has a credential (Anthropic, then OpenAI, then OpenRouter), and `createVela()` without `model` does the same, instead of reporting that no model is selected. The picked model is saved with the session (like pi), so resuming it keeps that model.
- The built-in price table (`PRICE_TABLE`) is gone: prices come from the model catalog or `cost` in `models.json`.
- **`--list-models` exits with code 1 when an extension failed to load.** The models that did load are still listed and the load errors go to stderr. pi exits 0 here; Vela fails loudly so scripts notice an incomplete list.

### Fixed

- A response cut off by the output token limit while calling tools no longer breaks the session (every later prompt failed with `AI_InvalidPromptError`): like pi, each truncated call gets an error result asking the model to re-issue it. See [Sessions](docs/sessions.md#truncated-responses).
- An aborted or failed turn keeps what it produced: tool calls that were running stay in the history, each paired with its result or `Operation aborted`, and a message cut off while streaming is kept in the session. Before, the whole step was dropped and the model didn't know a tool had already run. See [Sessions](docs/sessions.md#interrupted-and-failed-turns).
- A request that already started running tools is no longer sent again after an error, so tools don't run twice.
- Interactive mode no longer stays running and spins a CPU after its terminal closes: on SIGHUP it saves and exits even though restoring the terminal fails, and a read or write error on a dead terminal exits at once with code 129, like pi.
- When a request is retried, the interactive mode keeps the failed attempt's text marked `(response failed)` and shows the retry as a new message, instead of appending the retry to the old text.
- **The knowledge base no longer mixes vectors from different embedding models.** It records the embedder that built it, and when the configured one differs, ingesting and searching fail with an error naming both instead of returning meaningless scores. Switch back, or run `/rag clear` and ingest again. A knowledge base from 0.1.0 has no record: the configured embedder is assumed, recorded and a warning logged. See [rag](docs/built-in-extensions.md#rag).

### New Features

- **MCP servers** (built-in `mcp` extension, like pi's): configure servers in `~/.vela/mcp.json` or the trusted project's `.vela/mcp.json` (the `mcpServers` format of Claude Desktop and Claude Code), over stdio or streamable HTTP. Their tools are `mcp__<server>__<tool>`, deferred by default and loaded with `tool_search`; `exposure` / `toolExposure` make them `direct` or `hidden`. One set of connections serves all sessions of a Vela. `/mcp` shows server status and `/mcp reconnect <server>` reconnects. Guests cannot use MCP tools. SDK apps add `mcp({ servers })`. Not yet supported: OAuth sign-in, MCP resources and codemode. Uses the official `@modelcontextprotocol/sdk`. See [MCP servers](docs/mcp.md).
- Extension API: `unregisterTool(name)`, `onShutdown(handler)` (runs on `vela.dispose()`), and `registerTool()` returns the registered name. Tools can be registered at any time.
- `loadConfig()` returns `mcp` with the servers from `mcp.json`; `.vela/mcp.json` counts as project config that needs trust.
- **Context overflow recovery**: when the provider says the context is too long, Vela summarizes the history once and sends the step again, like pi (`compaction_end` with `reason: 'overflow'`). See [Sessions](docs/sessions.md#context-overflow).
- `session.getEntries()` returns the session's entries, including summarized messages and interrupted assistant messages.
- Calls a tool makes through `ctx.executeTool()` are recorded on its tool result in the session (`nestedCalls`, like pi), not sent to the model.
- **Anthropic prompt caching**: the system prompt, last tool and last message are sent as cache breakpoints, like pi. See [Sessions](docs/sessions.md#prompt-caching).
- **Automated releases**: `bun run release <patch|minor|x.y.z>` tags a release, and CI publishes it to npm with provenance and creates the GitHub release from this changelog.
- `edit_file` applies several disjoint edits in one call, falls back to fuzzy matching (trailing whitespace, smart quotes, Unicode dashes and spaces), keeps BOM and CRLF line endings, and records a diff and unified patch in the tool history. Ported from pi.
- `shellPath` setting and `createVela({ shellPath })` choose the shell of the `bash` tool.
- `withFileMutationQueue(path, fn)` is exported for extension tools that write files.
- **AGENTS.md / CLAUDE.md**: project instructions go into the system prompt, found like pi: `~/.vela/AGENTS.md`, then one file per directory from the filesystem root down to the working folder (`AGENTS.override.md`, `AGENTS.md`, `CLAUDE.md`, ...). Like pi they load whether or not the project is trusted; guest sessions don't get them. `--no-context-files` turns them off; the SDK takes `contextFiles` and exports `loadContextFiles()`. See [Context files](docs/settings.md#context-files).
- **Prompt templates**: `/<name> [args]` expands a Markdown template from `~/.vela/prompts/`, `.vela/prompts/` (trusted projects) or the new `prompts` setting, with pi's `$1`, `$@`, `${N:-default}` and `${@:N}` placeholders. Templates and skills show up in `/` completion and in RPC `get_commands` (with pi's `source` field). See [Prompt templates](docs/settings.md#prompt-templates).
- **More skill locations and options**: `.agents/skills/` in the project (up to the git root, trusted projects) and `~/.agents/skills/`; nested skill directories; `disable-model-invocation: true` for skills only you can run.
- **Appending to the system prompt**: `--append-system-prompt <text or file>` (repeatable), `~/.vela/APPEND_SYSTEM.md` and `.vela/APPEND_SYSTEM.md` (trusted projects), and the SDK's `appendSystemPrompt`. See [Settings](docs/settings.md#the-system-prompt).
- System prompt sections follow pi's order (rules, addendum, project context, skills, working directory, then extension sections), and the skills list no longer changes during a session, which keeps the prompt cache prefix stable.
- **`ctx.executeTool(name, args, { signal, onUpdate })`** lets a tool run another tool through the same permissions, hooks, `bash` check, confirmation and tool history as a model call, same as pi. Nested calls get ids `<parent>/<n>` and `parentToolCallId` on their events, and failures come back as `isError` results instead of throwing. See [Extensions](docs/extensions.md#registertool).
- **Streaming tool output**: `ctx.onUpdate(partialResult)` emits `tool_execution_update` (pi's event), and `bash` sends the tail of its output while it runs.
- **Session tree** (like pi): `/tree` moves to an earlier point of the session without losing the branch you leave (pick one of your messages to edit and resend it), optionally summarizing that branch (`branch_summary` entry) or labelling an entry (`label` entry). `/fork` continues in a new session from before an earlier message and `/clone` copies the current branch; the new session records `parentSession`, and `--fork <id>` does the same from the command line. The SDK has `navigateTree()`, `fork()`, `clone()`, `setLabel()`, `getTree()`, `getBranch()` and `getLeafId()`; unlike pi, `fork()` and `clone()` open the copy as another session and leave the original open. RPC gains pi's `get_tree`, `get_entries`, `get_fork_messages`, `fork` and `clone`, and extensions get pi's `session_before_tree`, `session_tree` and `session_before_fork` events. The file format stays version 2. See [Sessions](docs/sessions.md#session-tree).
- **Export**: `/export [path]`, `session.exportHtml()` / `exportJsonl()`, RPC `export_html` and `vela --export <id or file> [output]` write the current branch as a self-contained HTML page (or as JSONL). See [Sessions](docs/sessions.md#export).
- **Automatic compaction can be turned off** (pi's `compaction.enabled`): the `autoCompaction` setting, `createVela({ autoCompaction })`, `vela.session(id, { autoCompaction })`, `session.autoCompaction` and RPC `set_auto_compaction`. Off means no microcompaction, threshold summary or compact-and-retry on overflow; `/compact` still works. See [Sessions](docs/sessions.md#turning-automatic-compaction-off).
- **Extension messages, like pi**: `session.sendMessage({ customType, content, display, details }, { triggerTurn, deliverAs })` adds a custom message the model sees as a user message (`steer`, `followUp` and `nextTurn` delivery as in pi), `session.sendUserMessage(text)` sends input as if typed, and `session.appendEntry(customType, data)` saves extension state. They are on the session because one Vela serves many sessions. Custom messages are saved as `custom_message` entries, carry `custom` on their `message_start` / `message_end` events, and show in the TUI as a `[customType]` block when `display` is true. `before_agent_start` handlers can return `{ message }`. See [Extensions](docs/extensions.md#messages).
- **New extension events from pi**: `input` (rewrite or handle user input; `PromptOptions.source` says where it came from), `context` (change the messages of each request without touching the history), `before_provider_request` (change the AI SDK call options, including headers), `after_provider_response` (response headers) and `provider_stream_event` (raw provider chunks). `tool_call` and `tool_result` carry `parentToolCallId` for calls made through `ctx.executeTool()`. See [Extensions](docs/extensions.md#intercepting-events).
- **Tool metadata from pi**: `exposure` adds `model-only`, `codemode` and `hidden` to `direct` and `deferred`; `namespace` groups deferred tools (and is returned by `tool_search` with its `instructions`); `annotations` describe what a tool does. See [Tools](docs/tools.md#deferred-tools-and-tool_search).
- **Interactive mode tool blocks like pi's**: `bash` output streams into its block while it runs, with the elapsed time, and the collapsed block keeps the last 5 lines; `edit_file` shows a colored diff with changed words highlighted; other tools show the first 10 lines; calls made through `ctx.executeTool()` are listed inside the calling tool's block. See [CLI](docs/cli.md#tool-output).
- `tool_execution_end` has `details`: display data the model doesn't get, such as `edit_file`'s diff (pi's `result.details`). Extension tools set it by returning `new ToolExecutionResult(details, text)` (now exported) instead of a string.
- **`/copy`** copies the last answer to the clipboard, like pi (system clipboard tools, or OSC 52 over SSH).
- **`!command` and `!!command`** in interactive mode run a shell command yourself, like pi: `!` sends the command and its output to the model with your next message, `!!` keeps it out; Esc cancels. The SDK has `session.executeBash()` / `abortBash()` and RPC the `bash` / `abort_bash` commands; results are saved as `bash_execution` session entries, and output streams as `bash_execution_update` events. See [CLI](docs/cli.md#interactive-mode).
- A resumed session in interactive mode shows tool blocks as they were, with `edit_file` diffs and nested calls: tool messages in the session keep each tool's `details`.
- **`--tools` / `--no-tools` / `--exclude-tools`** (`-t` / `-nt` / `-xt`) choose the tools by name or `*` pattern, like pi; an entry that matches no tool is an error. **`--list-models [search]`** lists the configured models.
- **Built-in model catalog** generated from pi's (`@earendil-works/pi-ai`, MIT): the built-in providers list their models, and any known model id, built-in or from `models.json`, gets its context window, output limit, price, image input and thinking levels. `bun scripts/update-models.ts` regenerates it. See [Models](docs/models.md#the-model-catalog).
- **`openrouter` is a built-in provider** (`OPENROUTER_API_KEY`), with reasoning sent as OpenRouter's `reasoning: { effort }`.
- **`/login` and `/logout`** (like pi): store an API key, or sign in with **Sign in with ChatGPT** (use a ChatGPT Plus/Pro plan in the local terminal, through OpenAI's token sharing for open-source agents) or **OpenRouter** (creates a key). Credentials live in `~/.vela/auth.json` (pi's format, mode 0600) and take precedence over `models.json` and environment variables. OAuth tokens are refreshed before they expire, once across processes. Sign in with ChatGPT is for your own local use: channel sessions (Feishu) refuse it, and its token is only sent to api.openai.com. See [Credentials and /login](docs/models.md#credentials-and-login).
- Extensions can offer `/login` for their providers (`oauth`, `apiKeyLogin`) and read the credential per request with `ctx.credential()`. The SDK has `createVela({ credentials })`, `fileCredentialStore()`, `memoryCredentialStore()`, `vela.login()`, `vela.logout()` and `vela.loginProviders()`. See [Extensions](docs/extensions.md#registerprovider).
- **Model switching like pi**: the `/model` picker filters as you type, Ctrl+P / Shift+Ctrl+P cycle through the models in the new `enabledModels` setting (all available models when unset), and RPC gains `cycle_model` and `cycle_thinking_level`. See [Enabled models](docs/settings.md#enabled-models).
- `session.availableThinkingLevels()` lists the levels the current model supports.
- **`/rag clear`** deletes every chunk of the knowledge base, and `/rag` shows which embedder built it.
- `EmbeddingFn` has an optional `id` naming its model (set by `createEmbedder()`), and `createFauxEmbedder()` takes an `id` option.

### Changed

- Tools no longer share one lock across all sessions: `write_file` / `edit_file` queue per file, `bash` takes no lock, and a `sequential` tool only waits for calls in its own session. A long `bash` in one session no longer holds back other sessions (including channel senders).
- `bash` returns the last 2,000 lines or 50KB of output (was the last 3,000 characters) and ends with `Command exited with code N`, `Command timed out after N seconds` or `Command aborted` instead of `exit=N`.
- `read_file` pages default to 2,000 lines and at most 50KB (was 200 lines and 8,000 characters).

## [0.1.0] - 2026-10-09

First public release.

### New Features

- **Embeddable agent SDK**: `createVela()` assembles the model, tools, system prompt and extensions; `vela.session(id)` opens independent sessions that can run at the same time in one process. Sessions stream typed events, accept `steer` and `followUp` messages while running, and can switch model and thinking level between prompts. See [SDK](docs/sdk.md).
- **Terminal agent**: the `vela` command runs an interactive TUI built on pi-tui, a print mode (`-p`, piped stdin), a JSON event stream (`--mode json`) and a JSONL RPC mode (`--mode rpc`), plus `--help` and `--version`. See [CLI](docs/cli.md), [JSON mode](docs/json.md) and [RPC mode](docs/rpc.md).
- **pi-style extensions**: an extension is a function that registers tools, slash commands, model providers and channels and handles agent events. The CLI loads `.ts` extensions on Bun and on Node 22.18+ through Node's type stripping. See [Extensions](docs/extensions.md).
- **Built-in extensions**: cross-session memory, a RAG knowledge base (sqlite-vec + FTS5 hybrid search), web fetch and search, and a Feishu channel. See [Built-in extensions](docs/built-in-extensions.md) and [Channels](docs/channels.md).
- **Models and settings**: built-in `openai` and `anthropic` providers, more providers through `~/.vela/models.json`, thinking levels, and user and project `settings.json`; project settings, extensions and skills load only after you trust the project. See [Models](docs/models.md) and [Settings](docs/settings.md).
- **Long sessions**: tool result truncation, microcompaction and LLM summary compaction, loop detection, retries with backoff, and token and cost tracking (models with no known price show tokens only). Sessions are saved as versioned checkpoints. See [Sessions](docs/sessions.md) and [Session format](docs/session-format.md).
- **Offline testing**: `@glows777/vela/testing` provides a scripted faux model, a faux embedder, `createTestVela()`, and recording and replay of real runs; the CLI also has an offline demo model (`VELA_MODEL=mock`). See [Testing](docs/testing.md).
- **Session roles**: `owner`, `collaborator` and `guest` limit which tools a session can use, so channel senders don't get access to the machine; per-session `permissions` can only make a role stricter. Channels give each sender one session per conversation. See [Security](docs/security.md).
