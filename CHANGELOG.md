# Changelog

All notable changes to `@glows777/vela` are listed here. While Vela is on 0.x, a release that breaks the public API bumps the minor version and lists the break under **Breaking Changes** with how to migrate; patch releases don't break anything. See [API stability](docs/sdk.md#api-stability) for what counts as public.

## [Unreleased]

### Fixed

- Feishu topic prompts now prioritize the latest message after a task finishes, avoiding unsolicited repetitions of completed reports while preserving context for requested follow-ups and ongoing work.
- DeepSeek Responses requests preserve earlier assistant answers as text instead of unsupported server-side item references, so follow-ups can see reports already delivered. OpenAI requests, storage defaults and thinking settings are unchanged.

### Breaking Changes

- **Feishu topic runs now show live feedback.** Group inputs receive `OnIt` then `DONE`/`CrossMark`; one shared Stop card shows bounded tool progress and a 15-second heartbeat. Topic results and decision questions @-mention the original requester. Custom `FeishuTransport` implementations must return a message ID from `sendCard` and implement `patchCard`, `addReaction` and `removeReaction`. See [task feedback and permissions](docs/channels.md#task-feedback).

- **Feishu group tasks can now open topics.** The channel prompt distinguishes short direct answers from work handed off through `feishu_start_topic`; task execution does not block the channel. Original messages can be forwarded into same-group owned topics, and dispatch tools are hidden from topic sessions and DMs. Custom transports must implement `startTopic(messageId, task)` with a root/thread receipt and `forward(messageId, threadId)` with a message receipt. Existing send permission covers both; see [channel dispatch](docs/channels.md#channel-dispatch).

- **Feishu topics now have separate sessions.** Mentioning Vela inside a topic establishes its conversation; later replies from any member need no @ and automatically steer a running task. Each topic run has a Stop card that preserves context. Grant `im:message.group_msg` to receive untagged replies. The first mention in an unowned topic reads its full paginated history through the trigger timestamp; later mentions reuse stored context; top-level group messages and DM controls retain their existing behavior. Custom `FeishuTransport` implementations must add `listTopicMessages(threadId, pageToken?)`, returning ascending `{ items, pageToken? }` pages. Existing shared group history is not migrated into individual topics.

- **Custom Feishu transports must support run cards.** Implement `sendCard(chatId, card, replyToId?)` for Card 2.0 payloads and `start(onMessage, onAction)` with the v2 `card.action.trigger` callback and its toast response. Enable that callback subscription in Feishu's long-connection settings; existing message-send permissions cover the cards. See [Channels](docs/channels.md#run-controls).
- **History is Vela's `ModelMessage`, and an inline image is `{ type: 'image', data, mimeType }`.** `session.messages`, the `context` hook's `messages`, `message_end` events, RPC `get_messages`, and session `message` entries use this type. The image part stores base64 in `data` and a media type in `mimeType`. The AI SDK image part `{ type: 'image', image, mediaType }` is deprecated in ai@7. History that contains an image is not an AI SDK `ModelMessage`. `session.messages` is not assignable to the AI SDK `ModelMessage[]` type. Text-only history still works if you pass it to the AI SDK at runtime. To migrate, import `ModelMessage` from `@glows777/vela` for history and for a `context` handler. Map each stored image part to the file part `{ type: 'file', data, mediaType }` before you pass image history to `generateText` or another AI SDK call. Vela does that mapping on the provider request and leaves the saved image in place. See [Image input](docs/sdk.md#image-input) and [Messages](docs/session-format.md#messages).
- **Channels now share one owner session per enabled chat.** Feishu `chats` lists enabled chat_ids; `owners` now enables only those open_ids' direct chats. A deployment with only `owners` no longer answers in groups until each trusted group is listed in `chats`. Every member of an enabled chat has owner access to bash, files, memory and extensions. Groups run only on an @mention of this bot, include up to 50 recent history messages with cached display names, and reply to the triggering message. Empty `chats` logs a startup notice; unlisted chats are ignored and logged. Session ids change from `<channel>-<chat>-<sender>` to `<channel>-<chat>`; old per-sender files are kept but not combined or automatically resumed. Core SDK roles are unchanged. Custom channels default to owner and must enforce enablement before delivery. Custom `FeishuTransport` implementations need bot identity, contact lookup, history and reply methods. See [channel migration and required Feishu permissions](docs/channels.md#migration).

### Fixed

- **Headless session save failures were silent.** Channels now log the error with the session id and refuse new prompts after three consecutive failures until a successful write resets the count. Print mode (`-p`) reports save failures on stderr while keeping the answer on stdout.

- **A turn stopped at `summaryThreshold` when there was nothing to summarize.** A message above that threshold and below `maxInputTokens` is sent. Only a request over `maxInputTokens` stops the turn.
- **The loop-detection warning was broken English, stored as a user message, and fired one call late.** It now fires on the 10th identical call (a critical stop on the 20th). The sentence names that count. The session stores it as a custom message (`customType: loop`), so a resumed session does not show it as something you typed. The model still sees the text.
- **`--no-session` still wrote session files.** The transcript stayed in memory, and `/status` said `in-memory (not saved)`, but a tool turn still appended `tool-history.jsonl` and `usage/today.jsonl` under the data directory. Those, and long tool output, now stay out of the data directory. Tool history and long output use a temporary directory removed when the session closes. Memory and the knowledge base are unchanged. Usage totals stay available in `/status` and `/usage`.
- **The CLI never showed which `AGENTS.md` / `CLAUDE.md` files it loaded.** Print, JSON and RPC mode now print one `[context]` line on stderr. Interactive mode prints that line in the chat log at startup, and `/status` lists the same paths after `Context files:`. A file in the working folder is relative to it. A file under the home directory uses `~`, and a file under the agent directory outside the home directory uses `$VELA_DIR`. `--no-context-files` prints nothing.
- **The offline demo model (`VELA_MODEL=mock`) crashed Vela when you pressed Esc** while it was answering (`Controller is already closed`, exit 1). Its stream is now pull-based, so an interrupted answer just stops. `test parallel` and `test loop` called a `get_weather` tool that no longer exists and now use built-in tools, and any prompt containing "ls" inside a word ("tools", "details") no longer lists files.
- **`/status` disagreed with the footer and named a session file that did not exist yet.** The dollar amount now uses the same four-decimal rounding as the footer and `/usage` (`$0.0016`, not `$0.002` in one place and `$0.0016` in the other). A session that has not been saved says `not written yet (will save to …)` instead of a missing `.jsonl` path. Long paths shorten `~` under the home directory and `$VELA_DIR` only when the file is under the configured agent directory. The Path line is fitted to the terminal's display columns, so a session id is not broken across lines at 80 or 120 columns, and an unsaved session keeps `not written yet` even when the destination does not fit.
- **Shutdown failures no longer skip independent cleanup.** `vela.dispose()` and `session.close()` now reject with an `AggregateError` after their remaining cleanup attempts settle, including failures from shutdown hooks that were previously only logged. Callers should handle the rejection; repeated calls return the same result without retrying cleanup.
- **`vela.dispose()` now waits for asynchronous extension factories to settle** before tearing down their resources. A factory that never settles can therefore keep disposal pending indefinitely; no timeout or forced termination is implied.
- **The `memory` tool's `read` and `delete` accepted paths.** A file name such as `../../x` reached files outside the memory directory: `read` rewrote the file it read (adding a `lastReadAt` line and setting mode `0600`) and `delete` removed it, even in sessions whose permissions denied `bash` and file writes. Both now accept only a memory file name from the index.
- **Channel sessions were never closed**, so a long-running bot kept one session per conversation and sender in memory for as long as it ran. An idle channel session is now closed after 10 minutes (`createVela({ channelIdleMs })`) and resumed on the next message.
- **Guest system prompts included the tool call history guide**, with absolute paths of the data directory (which reveal the home directory and the project path) and instructions for tools a guest doesn't have. Guests no longer get it.
- **Print, JSON and RPC modes left commands running when stopped by a signal.** `bash` runs commands in their own process group, which outlived a `vela -p` killed with SIGTERM or Ctrl+C. These modes now abort the run, kill the commands, save the session and exit with 130 (SIGINT), 143 (SIGTERM) or 129 (SIGHUP); a second signal exits right away.
- **Feishu**: a message delivered twice is handled once; rich-text (`post`) messages are read as text instead of being dropped; images, files and other messages get a reply asking for text.
- **A second `vela.dispose()` or `session.close()` returned before the first one finished**, so a caller could exit before extensions' shutdown handlers and the final save ran. It now waits for the close in progress.
- **The knowledge base's embedding cache had no limit**: every ingested chunk's text and vector stayed in memory. It now keeps the 1000 most recently used texts per embedder.
- **`web_fetch` read the whole response into memory.** It now reads at most 5 MB and says when the page was cut.

### Added

- **Feishu Queue / Steer / Stop cards during a chat run.** Queue remains the default with one answer per message. Steer joins the active task for one combined reply; Stop aborts with a visible confirmation and cancels that run's pending steers while keeping other gateway messages queued. Choices are bound to the enabled chat and original run; repeated or expired callbacks cannot control later runs.
- **Images in SDK prompts and tool results.** Core prompts, extension hooks, RPC, `read_file` and MCP share inline image content with lazy Photon WASM normalization (a new runtime dependency). Native tool images work with Anthropic/Responses; Chat-compatible providers receive request-only user attachments. CLI/TUI attachment entry is planned separately.

- **Core image input.** `PromptOptions.images` attaches images to `prompt`, `steer`, and `followUp`. `sendUserMessage` accepts a string or an array of text and image parts. `InputEvent.images` exposes the same parts to the `input` hook. RPC `prompt`, `steer`, and `follow_up` accept an `images` array. The package exports `ImageContent`, `ModelMessage`, `UserContent`, and `TextContent`. An image is `{ type: 'image', data, mimeType }`. Saved history keeps the normalized image. A text-only model receives a placeholder in that request only. See [Image input](docs/sdk.md#image-input).
- `/status` in interactive mode: a session overview with the id, file path (not written yet until the first save; in-memory when the session is not saved; custom storage when the location is not reported), working directory, model, thinking level, role, message count, context estimate and token usage. `session.persistence` is `{ type: 'file', path }`, `{ type: 'memory' }`, or `{ type: 'unknown' }` when a custom storage does not say. The dollar amount matches the footer.
- `createVela({ channelIdleMs })`, and `channelIdleMs` in `createTestVela()`.
- `feishu({ transport })` and the `FeishuTransport` / `FeishuMessageEvent` types, so the Feishu channel can be tested without a Feishu app.

## [0.2.0] - 2026-10-11

### Breaking Changes

- **Events now have pi's shape.** `message` is replaced by `message_start` / `message_end`; `text_delta` and `thinking_delta` by `message_update` (`assistantMessageEvent.type` is `text_delta` / `thinking_delta` and the text is in `delta`, alongside `text_start` / `text_end`, `thinking_start` / `thinking_end` and `toolcall_start` / `toolcall_delta` / `toolcall_end`); `tool_call` by `tool_execution_start` (`input` is now `args`); `tool_result` and `tool_error` by `tool_execution_end` (`output` / `error` is now `result`, with `isError` and `durationMs`); `retry` by `auto_retry_start` (`maxRetries` → `maxAttempts`, `error` → `errorMessage`) and the new `auto_retry_end`. `turn_end` has `message` and `toolResults` instead of `needsToolCall`; `agent_end` adds `messages`. The assistant `message_end` carries `stopReason` (`stop`, `toolUse`, `length`, `aborted`, `error`) and `errorMessage`. `--mode json`, `--mode rpc` and SDK subscribers see the new events. To migrate, print `message_update` events whose `assistantMessageEvent.type` is `text_delta`, and read final messages from `message_end`. See [SDK events](docs/sdk.md#events) and [JSON mode](docs/json.md). The extension `tool_call` / `tool_result` interception events are unchanged.
- **`bash` has no default timeout** (same as pi). The model passes an optional `timeout` in seconds instead. `limits.bashTimeoutMs` is removed; setting it in `settings.json` or `createVela({ limits })` is now an "unknown key" error. Remove the key.
- **`edit_file` takes pi's parameters**: `{ path, edits: [{ oldText, newText }] }` instead of `old_string` / `new_string`. A text that is not found, found more than once or overlapping another edit is now a tool error instead of a successful result describing the problem. Faux scenarios that call `edit_file` need the new arguments.
- **`ToolDefinition.isConcurrencySafe` is replaced by `executionMode`** (`'parallel'`, the default, or `'sequential'`, same as pi). Drop `isConcurrencySafe: true`; replace `isConcurrencySafe: false` with `executionMode: 'sequential'` if the tool must not run alongside the session's other calls. Registering a tool that still sets `isConcurrencySafe` throws, so the change is not silently ignored.
- **Skills use the Agent Skills format and the model loads them itself** (like pi). The system prompt now lists each skill's name, description and `SKILL.md` path, and the model reads the file with `read_file` when a task matches. `description` is required (skills without one are skipped with a warning) and the name comes from the `name` front matter, falling back to the directory name. `when_to_use` is no longer read: fold it into `description`. `/skill load`, `/skill unload`, `/<skill-name>` and the per-session active state are gone: send a skill yourself with `/skill:<name> [instruction]`, which now works in every mode and in `session.prompt()`. When two skills share a name, the first one found wins (project before user) instead of the last. See [Skills](docs/settings.md#skills).
- `FixtureSkill` in `@glows777/vela/testing` drops `whenToUse` and gains `disableModelInvocation`.
- **`ToolDefinition.isReadOnly` is replaced by `annotations`** (pi's and MCP's `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`). Replace `isReadOnly: true` with `annotations: { readOnlyHint: true }`. Registering a tool that still sets `isReadOnly` throws.
- **A failed `bash` command is an error result** (same as pi): a non-zero exit, a timeout or an abort ends with `tool_execution_end` `isError: true`, and the model gets the output preview and status as the error text. Tools returning a `ToolExecutionResult` with `isError` are error results too. Code that read the status line from a successful result should check `isError`.
- `tool_search` is `model-only`: other tools cannot run it with `ctx.executeTool()`.
- **Sessions are an append-only log in pi's format (session file version 2).** Each message is appended to the session as it enters the history instead of the whole history being saved when `prompt()` ends, so a crash loses at most the step in progress. Like pi, a summary appends a `compaction` entry and folded tool output a `context_edit` entry; the original messages stay in the file. Model, thinking level and name are entries too. Version 1 files are converted when loaded and rewritten in the new format. See [Session format](docs/session-format.md).
- **`SessionStorage` has `load` / `append` instead of `load` / `save`**, and `SessionCheckpoint` is removed. `load(id)` returns the header and entries (`SessionFileEntry[]`), `append(id, entries)` adds entries in order. Custom storages store entries as given; `summarizeSession(id, entries)` builds a `list()` row and `migrateSessionV1(id, lines)` converts data saved by the old checkpoint storage. See [Session storage](docs/sdk.md#session-storage).
- **Summaries emit pi's `compaction_start` / `compaction_end`** (`reason`: `threshold`, `manual` or `overflow`; `compaction_end` has `result`, `aborted`, `willRetry`, `errorMessage`) instead of the `context` event's `summary`, `compact` and `overflow` actions; `context` remains for microcompaction (`micro`) and `summary-required`. The RPC `compact` command returns the compaction result.
- **The `context` event is renamed `context_prepare`** (same fields: `action` `micro` or `summary-required`, token counts). `context` is now pi's extension hook that changes the messages of each request. Subscribers, `--mode json` and `--mode rpc` clients that read `context` should read `context_prepare`.
- **An assistant message cut off while it streamed (abort or failure) is no longer sent to the model**, like pi: it is appended to the session with `stopReason: 'aborted'` or `'error'` but left out of `session.messages`. A message the model finished, whose tools were running, still stays in the history with its tool calls answered.
- **`tool_search` searches by keyword and loads tools instead of returning schemas** (like pi). It takes `query` (keywords, or exact tool names separated by commas) and an optional `limit` (default 8), ranks deferred tools with BM25 and loads the best matches for the model's next call; the result lists the loaded tools and each namespace's `instructions` once. The system prompt names each namespace (such as an MCP server) once with its tool count instead of listing its tools. Faux scenarios that read the old JSON result of `tool_search` need updating. See [Tools](docs/tools.md#deferred-tools-and-tool_search).
- An extension tool whose name already starts with `<extension name>_` is no longer prefixed again (`web_x` from the `web` extension stays `web_x`, not `web_web_x`).
- **Prompting a saved session that was not resumed fails** with `Session <id> already has saved history: call resume() to continue it, or use another session id`. Before, the old history was silently overwritten at the end of the prompt. Call `await session.resume()` first, or use a new id.
- **The built-in `openai` provider uses the Responses API** (`openai-responses`, like pi) instead of Chat Completions. For an OpenAI-compatible service behind `OPENAI_API_BASE_URL` that only speaks Chat Completions, set `"api": "openai-completions"` on `openai` in `~/.vela/models.json`, or add the service as its own provider.
- **An unsupported thinking level is clamped instead of failing** (like pi): a model with `reasoning: false` runs with `off`, and `xhigh` / `max` fall back to `high` unless the model's catalog entry supports them. `max` is now sent to the AI SDK as `max` (it was `xhigh`), and `off` sends `reasoning: 'none'` to models without `reasoning: false`. `/thinking`, Shift+Tab and RPC `get_available_thinking_levels` offer only the levels the model supports. See [Thinking levels](docs/models.md#thinking-levels).
- **`vela.models()`, `/model`, `--list-models` and RPC `get_available_models` list only available models**: those of providers that have a credential, like pi. `vela.models({ all: true })` returns every listed model.
- **`ProviderDefinition.createModel(id, ctx)`** gets a second argument with `ctx.credential()`; providers that ignore it keep working. `ModelRegistry` takes a `CredentialStore` as its second argument.
- **Without `--model`, `defaultModel` or `OPENAI_API_MODEL_NAME`, Vela picks pi's default model** of the first built-in provider that has a credential (Anthropic, then OpenAI, then OpenRouter), and `createVela()` without `model` does the same, instead of reporting that no model is selected. The picked model is saved with the session (like pi), so resuming it keeps that model.
- The built-in price table (`PRICE_TABLE`) is gone: prices come from the model catalog or `cost` in `models.json`.
- **`--list-models` exits with code 1 when an extension failed to load.** The models that did load are still listed and the load errors go to stderr. pi exits 0 here; Vela fails loudly so scripts notice an incomplete list.

### Fixed

- A response cut off by the output token limit while calling tools no longer breaks the session (every later prompt failed with `AI_InvalidPromptError`): like pi, each truncated call gets an error result asking the model to re-issue it. See [Sessions](docs/sessions.md#truncated-responses).
- An aborted or failed turn keeps what it produced: tool calls that were running stay in the history, each paired with its result or `Operation aborted`, and a message cut off while streaming is kept in the session. Before, the whole step was dropped and the model didn't know a tool had already run. See [Sessions](docs/sessions.md#interrupted-and-failed-turns).
- A request that already started running tools is no longer sent again after an error, so tools don't run twice.
- Interactive mode no longer stays running and spins a CPU after its terminal closes: on SIGHUP it saves and exits even though restoring the terminal fails, and a read or write error on a dead terminal exits at once with code 129, like pi.
- When a request is retried, the interactive mode keeps the failed attempt's text marked `(response failed)` and shows the retry as a new message, instead of appending the retry to the old text.
- **The knowledge base no longer mixes vectors from different embedding models.** It records the embedder that built it, and when the configured one differs, ingesting and searching fail with an error naming both instead of returning meaningless scores. Switch back, or run `/rag clear` and ingest again. A knowledge base from 0.1.0 has no record: the configured embedder is assumed, recorded and a warning logged. See [rag](docs/built-in-extensions.md#rag).

### New Features

- **MCP servers** (built-in `mcp` extension, like pi's): configure servers in `~/.vela/mcp.json` or the trusted project's `.vela/mcp.json` (the `mcpServers` format of Claude Desktop and Claude Code), over stdio or streamable HTTP. Their tools are `mcp__<server>__<tool>`, deferred by default and loaded with `tool_search`; `exposure` / `toolExposure` make them `direct` or `hidden`. One set of connections serves all sessions of a Vela. `/mcp` shows server status and `/mcp reconnect <server>` reconnects. Guests cannot use MCP tools. SDK apps add `mcp({ servers })`. Not yet supported: OAuth sign-in, MCP resources and codemode. Uses the official `@modelcontextprotocol/sdk`. See [MCP servers](docs/mcp.md).
- Extension API: `unregisterTool(name)`, `onShutdown(handler)` (runs on `vela.dispose()`), and `registerTool()` returns the registered name. Tools can be registered at any time.
- `loadConfig()` returns `mcp` with the servers from `mcp.json`; `.vela/mcp.json` counts as project config that needs trust.
- **Context overflow recovery**: when the provider says the context is too long, Vela summarizes the history once and sends the step again, like pi (`compaction_end` with `reason: 'overflow'`). See [Sessions](docs/sessions.md#context-overflow).
- `session.getEntries()` returns the session's entries, including summarized messages and interrupted assistant messages.
- Calls a tool makes through `ctx.executeTool()` are recorded on its tool result in the session (`nestedCalls`, like pi), not sent to the model.
- **Anthropic prompt caching**: the system prompt, last tool and last message are sent as cache breakpoints, like pi. See [Sessions](docs/sessions.md#prompt-caching).
- **Automated releases**: `bun run release <patch|minor|x.y.z>` tags a release, and CI publishes it to npm with provenance and creates the GitHub release from this changelog.
- `edit_file` applies several disjoint edits in one call, falls back to fuzzy matching (trailing whitespace, smart quotes, Unicode dashes and spaces), keeps BOM and CRLF line endings, and records a diff and unified patch in the tool history. Ported from pi.
- `shellPath` setting and `createVela({ shellPath })` choose the shell of the `bash` tool.
- `withFileMutationQueue(path, fn)` is exported for extension tools that write files.
- **AGENTS.md / CLAUDE.md**: project instructions go into the system prompt, found like pi: `~/.vela/AGENTS.md`, then one file per directory from the filesystem root down to the working folder (`AGENTS.override.md`, `AGENTS.md`, `CLAUDE.md`, ...). Like pi they load whether or not the project is trusted; guest sessions don't get them. `--no-context-files` turns them off; the SDK takes `contextFiles` and exports `loadContextFiles()`. See [Context files](docs/settings.md#context-files).
- **Prompt templates**: `/<name> [args]` expands a Markdown template from `~/.vela/prompts/`, `.vela/prompts/` (trusted projects) or the new `prompts` setting, with pi's `$1`, `$@`, `${N:-default}` and `${@:N}` placeholders. Templates and skills show up in `/` completion and in RPC `get_commands` (with pi's `source` field). See [Prompt templates](docs/settings.md#prompt-templates).
- **More skill locations and options**: `.agents/skills/` in the project (up to the git root, trusted projects) and `~/.agents/skills/`; nested skill directories; `disable-model-invocation: true` for skills only you can run.
- **Appending to the system prompt**: `--append-system-prompt <text or file>` (repeatable), `~/.vela/APPEND_SYSTEM.md` and `.vela/APPEND_SYSTEM.md` (trusted projects), and the SDK's `appendSystemPrompt`. See [Settings](docs/settings.md#appending-to-the-system-prompt).
- System prompt sections follow pi's order (rules, addendum, project context, skills, working directory, then extension sections), and the skills list no longer changes during a session, which keeps the prompt cache prefix stable.
- **`ctx.executeTool(name, args, { signal, onUpdate })`** lets a tool run another tool through the same permissions, hooks, `bash` check, confirmation and tool history as a model call, same as pi. Nested calls get ids `<parent>/<n>` and `parentToolCallId` on their events, and failures come back as `isError` results instead of throwing. See [Extensions](docs/extensions.md#registertool).
- **Streaming tool output**: `ctx.onUpdate(partialResult)` emits `tool_execution_update` (pi's event), and `bash` sends the tail of its output while it runs.
- **Session tree** (like pi): `/tree` moves to an earlier point of the session without losing the branch you leave (pick one of your messages to edit and resend it), optionally summarizing that branch (`branch_summary` entry) or labelling an entry (`label` entry). `/fork` continues in a new session from before an earlier message and `/clone` copies the current branch; the new session records `parentSession`, and `--fork <id>` does the same from the command line. The SDK has `navigateTree()`, `fork()`, `clone()`, `setLabel()`, `getTree()`, `getBranch()` and `getLeafId()`; unlike pi, `fork()` and `clone()` open the copy as another session and leave the original open. RPC gains pi's `get_tree`, `get_entries`, `get_fork_messages`, `fork` and `clone`, and extensions get pi's `session_before_tree`, `session_tree` and `session_before_fork` events. The file format stays version 2. See [Sessions](docs/sessions.md#session-tree).
- **Export**: `/export [path]`, `session.exportHtml()` / `exportJsonl()`, RPC `export_html` and `vela --export <id or file> [output]` write the current branch as a self-contained HTML page (or as JSONL). See [Sessions](docs/sessions.md#export).
- **Automatic compaction can be turned off** (pi's `compaction.enabled`): the `autoCompaction` setting, `createVela({ autoCompaction })`, `vela.session(id, { autoCompaction })`, `session.autoCompaction` and RPC `set_auto_compaction`. Off means no microcompaction, threshold summary or compact-and-retry on overflow; `/compact` still works. See [Sessions](docs/sessions.md#turning-automatic-compaction-off).
- **Extension messages, like pi**: `session.sendMessage({ customType, content, display, details }, { triggerTurn, deliverAs })` adds a custom message the model sees as a user message (`steer`, `followUp` and `nextTurn` delivery as in pi), `session.sendUserMessage(text)` sends input as if typed, and `session.appendEntry(customType, data)` saves extension state. They are on the session because one Vela serves many sessions. Custom messages are saved as `custom_message` entries, carry `custom` on their `message_start` / `message_end` events, and show in the TUI as a `[customType]` block when `display` is true. `before_agent_start` handlers can return `{ message }`. See [Extensions](docs/extensions.md#messages).
- **New extension events from pi**: `input` (rewrite or handle user input; `PromptOptions.source` says where it came from), `context` (change the messages of each request without touching the history), `before_provider_request` (change the AI SDK call options, including headers), `after_provider_response` (response headers) and `provider_stream_event` (raw provider chunks). `tool_call` and `tool_result` carry `parentToolCallId` for calls made through `ctx.executeTool()`. See [Extensions](docs/extensions.md#intercepting-events).
- **Tool metadata from pi**: `exposure` adds `model-only`, `codemode` and `hidden` to `direct` and `deferred`; `namespace` groups deferred tools (and is returned by `tool_search` with its `instructions`); `annotations` describe what a tool does. See [Tools](docs/tools.md#deferred-tools-and-tool_search).
- **Interactive mode tool blocks like pi's**: `bash` output streams into its block while it runs, with the elapsed time, and the collapsed block keeps the last 5 lines; `edit_file` shows a colored diff with changed words highlighted; other tools show the first 10 lines; calls made through `ctx.executeTool()` are listed inside the calling tool's block. See [CLI](docs/cli.md#tool-output).
- `tool_execution_end` has `details`: display data the model doesn't get, such as `edit_file`'s diff (pi's `result.details`). Extension tools set it by returning `new ToolExecutionResult(details, text)` (now exported) instead of a string.
- **`/copy`** copies the last answer to the clipboard, like pi (system clipboard tools, or OSC 52 over SSH).
- **`!command` and `!!command`** in interactive mode run a shell command yourself, like pi: `!` sends the command and its output to the model with your next message, `!!` keeps it out; Esc cancels. The SDK has `session.executeBash()` / `abortBash()` and RPC the `bash` / `abort_bash` commands; results are saved as `bash_execution` session entries, and output streams as `bash_execution_update` events. See [CLI](docs/cli.md#interactive-mode).
- A resumed session in interactive mode shows tool blocks as they were, with `edit_file` diffs and nested calls: tool messages in the session keep each tool's `details`.
- **`--tools` / `--no-tools` / `--exclude-tools`** (`-t` / `-nt` / `-xt`) choose the tools by name or `*` pattern, like pi; an entry that matches no tool is an error. **`--list-models [search]`** lists the configured models.
- **Built-in model catalog** generated from pi's (`@earendil-works/pi-ai`, MIT): the built-in providers list their models, and any known model id, built-in or from `models.json`, gets its context window, output limit, price, image input and thinking levels. `bun scripts/update-models.ts` regenerates it. See [Models](docs/models.md#the-model-catalog).
- **`openrouter` is a built-in provider** (`OPENROUTER_API_KEY`), with reasoning sent as OpenRouter's `reasoning: { effort }`.
- **`/login` and `/logout`** (like pi): store an API key, or sign in with **Sign in with ChatGPT** (use a ChatGPT Plus/Pro plan in the local terminal, through OpenAI's token sharing for open-source agents) or **OpenRouter** (creates a key). Credentials live in `~/.vela/auth.json` (pi's format, mode 0600) and take precedence over `models.json` and environment variables. OAuth tokens are refreshed before they expire, once across processes. Sign in with ChatGPT is for your own local use: channel sessions (Feishu) refuse it, and its token is only sent to api.openai.com. See [Credentials and /login](docs/models.md#credentials-and-login).
- Extensions can offer `/login` for their providers (`oauth`, `apiKeyLogin`) and read the credential per request with `ctx.credential()`. The SDK has `createVela({ credentials })`, `fileCredentialStore()`, `memoryCredentialStore()`, `vela.login()`, `vela.logout()` and `vela.loginProviders()`. See [Extensions](docs/extensions.md#registerprovider).
- **Model switching like pi**: the `/model` picker filters as you type, Ctrl+P / Shift+Ctrl+P cycle through the models in the new `enabledModels` setting (all available models when unset), and RPC gains `cycle_model` and `cycle_thinking_level`. See [Enabled models](docs/settings.md#enabled-models).
- `session.availableThinkingLevels()` lists the levels the current model supports.
- **`/rag clear`** deletes every chunk of the knowledge base, and `/rag` shows which embedder built it.
- `EmbeddingFn` has an optional `id` naming its model (set by `createEmbedder()`), and `createFauxEmbedder()` takes an `id` option.

### Changed

- Tools no longer share one lock across all sessions: `write_file` / `edit_file` queue per file, `bash` takes no lock, and a `sequential` tool only waits for calls in its own session. A long `bash` in one session no longer holds back other sessions (including channel senders).
- `bash` returns the last 2,000 lines or 50KB of output (was the last 3,000 characters) and ends with `Command exited with code N`, `Command timed out after N seconds` or `Command aborted` instead of `exit=N`.
- `read_file` pages default to 2,000 lines and at most 50KB (was 200 lines and 8,000 characters).

## [0.1.0] - 2026-10-09

First public release.

### New Features

- **Embeddable agent SDK**: `createVela()` assembles the model, tools, system prompt and extensions; `vela.session(id)` opens independent sessions that can run at the same time in one process. Sessions stream typed events, accept `steer` and `followUp` messages while running, and can switch model and thinking level between prompts. See [SDK](docs/sdk.md).
- **Terminal agent**: the `vela` command runs an interactive TUI built on pi-tui, a print mode (`-p`, piped stdin), a JSON event stream (`--mode json`) and a JSONL RPC mode (`--mode rpc`), plus `--help` and `--version`. See [CLI](docs/cli.md), [JSON mode](docs/json.md) and [RPC mode](docs/rpc.md).
- **pi-style extensions**: an extension is a function that registers tools, slash commands, model providers and channels and handles agent events. The CLI loads `.ts` extensions on Bun and on Node 22.18+ through Node's type stripping. See [Extensions](docs/extensions.md).
- **Built-in extensions**: cross-session memory, a RAG knowledge base (sqlite-vec + FTS5 hybrid search), web fetch and search, and a Feishu channel. See [Built-in extensions](docs/built-in-extensions.md) and [Channels](docs/channels.md).
- **Models and settings**: built-in `openai` and `anthropic` providers, more providers through `~/.vela/models.json`, thinking levels, and user and project `settings.json`; project settings, extensions and skills load only after you trust the project. See [Models](docs/models.md) and [Settings](docs/settings.md).
- **Long sessions**: tool result truncation, microcompaction and LLM summary compaction, loop detection, retries with backoff, and token and cost tracking (models with no known price show tokens only). Sessions are saved as versioned checkpoints. See [Sessions](docs/sessions.md) and [Session format](docs/session-format.md).
- **Offline testing**: `@glows777/vela/testing` provides a scripted faux model, a faux embedder, `createTestVela()`, and recording and replay of real runs; the CLI also has an offline demo model (`VELA_MODEL=mock`). See [Testing](docs/testing.md).
- **Session roles**: `owner`, `collaborator` and `guest` limit which tools a session can use, so channel senders don't get access to the machine; per-session `permissions` can only make a role stricter. Channels give each sender one session per conversation. See [Security](docs/security.md).
